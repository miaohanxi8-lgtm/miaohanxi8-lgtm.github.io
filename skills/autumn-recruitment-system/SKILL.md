# 秋招作战系统

## 公开模板配置

- 本仓库版本是可复用的脱敏模板；先将 `references/notion-system.md` 中的示例页面、数据源与视图定位符替换为自己的 Notion 资源。
- QQ 邮箱地址与授权码只通过环境变量或 Windows 当前用户加密存储提供，绝不写入 Skill、仓库或 Notion。

## 入口与数据边界

- 'FLO.W 进阶版'首页是唯一日常入口；保持首页布局、顶部早报、任务、日程和底部面试日历位置不变。
- 每次先读取最新求职画像和相关 Notion 数据源结构，不复制静态全量画像。
- 不读取或链接秋招作战中心及面试准备、复盘、问题、简历、经历素材导航页；数据库及数据库模板继续使用。
- 不做岗位推荐、匹配评分、投递优先级或投递策略判断。
- 默认只读。只有用户请求变更、邮件同步规则明确要求写回或正在完成练习/复盘闭环时才写入。

## 场景路由

1. 每日 QQ 邮件、早报、晚间自动化、补跑：先读 [邮件同步规则](references/mail-sync.md)，再读 [Notion 数据映射](references/notion-system.md)；涉及今日专注、心情、打分或明日计划校准时再读 [每日复盘](references/daily-review.md)。
2. 真人面试邀请、改期、取消、准备、模拟、外部面经或用户图片：读 [面试链路](references/interview-workflow.md)。
3. 面试后复盘、原始问题、Q&A、对话 Case、专项练习、能力缺口、简历优化：读 [知识与能力闭环](references/knowledge-loop.md)。
4. 每日复盘、专注统计、心情记录、今日整体打分：读 [每日复盘](references/daily-review.md) 与 [Notion 数据映射](references/notion-system.md)；若复盘中涉及模拟或面试沉淀，再按场景补读对应闭环规则。
5. 查看完整秋招状态：读 [Notion 数据映射](references/notion-system.md) 与 [知识与能力闭环](references/knowledge-loop.md)，只读汇总；每日早报只输出行动、增量和当天能力重点，不重复完整状态快照。
6. 人工纠错：先精确查找所有相关岗位、任务、真实/模拟场次、原始问题、Q&A、练习、每日复盘和能力节点，再统一修正；对象不能唯一确定时先确认。

## 确定性脚本

- QQ 邮件只读抓取、MIME 解码、附件元数据提取、关键词预筛、UID 状态推进和原子 JSON 写入使用 [QQ 邮件脚本](scripts/qq_job_mail/qq_mail_export.py)，不要在临时工作目录中重写这些逻辑。附件内容永不保存到本地。
- 凭据初始化使用 `scripts/qq_job_mail/setup_qq_credentials.ps1`；运行入口使用 `scripts/qq_job_mail/run_qq_mail.ps1`。脚本代码与运行数据分离，禁止把授权码、密钥、邮件正文、附件、`pending_mail.json` 或 `state.json` 打包进 Skill。
- 邮件字段标准化、严格证据匹配、每日模拟/真人面试五对象/早报/UID 提交校验和历史耗时计算使用 [规则引擎](scripts/recruitment_rules.py)；需要运行这些命令时先读 [脚本与数据契约](references/script-contracts.md)。不要让模型重复手工完成脚本已经覆盖的机械计算。
- 确定性脚本只能产生候选、唯一精确命中和错误报告；`ambiguous`、岗位归属、申请链歧义、终态语义、Q&A 合并和能力证据升级仍按相关参考规则复核。
- 运行数据占用检查使用 QQ 邮件脚本的 `storage-report`；日常运行文件使用固定文件名覆盖，不创建附件目录或历史邮件归档。

## 每日模拟面试常驻规则

- 每天安排恰好一次模拟面试，用于保持面试手感并产生能力图谱的新证据。
- 若今天已有真人面试对应的模拟待办，直接把它作为当天练习，不再创建通用模拟待办。
- 若今天没有针对性模拟待办，则按邮件早报规则创建当天唯一的通用模拟待办；未来 7 天有真人面试时，练习内容优先针对最近一场，但不得改动该真人面试自带模拟待办的排期。这是用户明确授权的单日例外，不扩展为批量学习任务。
- 模拟完成后，按知识闭环区分模拟中实际问题、整场练习记录、Q&A 和能力节点，不能只更新自我感觉。

## 共同安全边界

- 邮箱永远只读：禁止发信、删信、移动、标记已读或修改邮件。
- 不输出、回显或写入邮箱授权码及其他凭据。
- 发件人必须进入去重证据链，但绝不能单独证明是同一岗位或申请链。
- Notion 精确识别优先使用完整数据库视图快照，在内存中按严格字段等值匹配，再 fetch 候选页面复核；SQL 查询不是日常前置条件。视图分页不完整、候选不能唯一确认且 SQL 备用查询也不可用时，停止写入；不得用模糊或语义搜索替代精确去重。
- 事实、用户判断和模型推断分开记录；缺失字段使用“公司待确认”或“岗位待确认”，不得猜测。
- 状态原则上只前进；Offer、拒信、背调、完成、取消等终态必须有明确依据。
- 不复制整封邮件或大段外部面经，只保留完成工作所需的结构化信息。
- 仅当岗位、面试、任务/日程和早报全部成功后才提交邮件 max_uid。

## 结束前检查

- 检查是否把原始问题、Q&A、练习记录和能力节点混写。
- 检查当天是否恰好有一次模拟面试行动，且没有同时创建针对性模拟与通用模拟两个待办。
- 检查真人面试是否恰好有两个面试页、一个日程和两个待办。
- 检查笔试、测评、AI 测评和真人面试相关任务的“下一步做什么？”是否包含可点击的首选入口，以及邮件明确给出的执行必需信息；不得只写泛化动作。
- 检查改期/取消是否同步到五个对象。
- 检查早报是否使用“今日行动、最新变化、未来 7 天、待补全与需确认”四段式结构；同一事实只出现一次。“今日行动”应结合历史任务与专注记录给出 6–8 小时净工作量的完整计划，并在具体任务中包含有证据的能力补缺。
- 检查晚间自动化是否先读取当天日记和情绪打卡，并在当天日记中补充或更新“秋招每日复盘”区块，再生成目标日期为明天的早报；打分应检查简历投递/投递推进、每日模拟面试、能力图谱补充、今日任务完成、心情状态和休息娱乐；早报只引用复盘结论和调整点，不复制整篇日记。
- 检查日常读取是否优先走 view mode，并避免按邮件或对象重复消耗 SQL 查询额度。
- 检查是否误建学习任务、岗位推荐或普通宣传岗位。
