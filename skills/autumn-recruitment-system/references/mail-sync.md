# 每日 QQ 邮件与早报

## 运行与幂等

- 时区固定 Asia/Shanghai。
- 先按 [Notion 数据映射](notion-system.md) 读取早报完整索引，在本地严格匹配日期和状态；若当天已有状态“已生成”的记录，不重复执行。日常检查不使用 SQL mode。
- 错过 08:00 时，在下一次运行机会补生成当天早报。
- 脚本位置相对本 Skill 固定为 `scripts/qq_job_mail/qq_mail_export.py`；不要依赖某个带日期的工作目录。
- 推荐入口：`powershell -NoProfile -ExecutionPolicy Bypass -File scripts/qq_job_mail/run_qq_mail.ps1 fetch -Days 7`。也可直接运行 `python scripts/qq_job_mail/qq_mail_export.py fetch --days 7`。
- 运行数据默认位于 `%LOCALAPPDATA%\Codex\autumn-recruitment-system\qq_job_mail`；可通过 `AUTUMN_RECRUITMENT_MAIL_DATA_DIR` 或 `--data-dir`/`-DataDir` 显式覆盖。以脚本输出中的 `pending_file` 为准读取 `pending_mail.json`，不要猜测路径。
- 首次配置运行 `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/qq_job_mail/setup_qq_credentials.ps1`。也可在当前进程中提供 `QQ_MAIL_ADDRESS` 与 `QQ_MAIL_AUTH_CODE`；不得将它们写入 Skill。
- 凭据未配置或登录失败时，不修改 Notion；说明失败原因并提醒重新配置 QQ IMAP/SMTP 授权码。
- 抓取完成后按 [脚本与数据契约](script-contracts.md) 运行 `normalize-mails`，输出到运行数据目录固定文件 `normalized_mail.json` 并每轮覆盖；后续索引和精确匹配使用标准化结果，不重复手工解析主题、发件地址、域名、编号、链接和日期候选。
- `pending_mail.json` 每轮原子覆盖，不累计历史正文。邮件附件内容永不保存到本地；求职候选邮件只保留文件名、MIME 类型和大小元数据，`saved_path=null`，`skipped_reason=attachment_storage_disabled`。运行目录不创建附件目录。

## 低额度读取流程

1. 抓取邮件后、任何 Notion 写入前，用 view mode 各加载一次早报、岗位、面试、任务和能力图谱完整索引；生成耗时计划时再加载专注历史索引。
2. 每个视图使用 page_size=100 并完成全部必要分页。岗位、面试、任务和早报必须读到 has_more=false；专注历史按开始时间倒序读取到 90 天边界即可。
3. 把视图快照映射为 [脚本与数据契约](script-contracts.md) 的 `records.json`，运行规则引擎 `match`。所有 messages 共用同一份标准化候选和记录快照；仅 `unique_match` 可进入页面复核，`ambiguous` 不得自动写入。
4. 命中候选页面后，通过页面 URL fetch 复核；创建或更新成功后立即把新属性和 URL 写回内存索引，避免同一批邮件内重复创建。
5. 正常流程不调用 SQL mode。只有视图缺字段或候选冲突时，才把本轮所有未决候选合并为每个数据库最多一次备用 SQL 查询；禁止在循环中逐封邮件查询。
6. SQL 额度错误不重试、不直接要求升级套餐：完整视图快照可用时继续；view mode 同样失败、分页不完整或候选仍不唯一时，才停止写入并保留 UID。

## 邮件去重证据顺序

1. 邮件 ID + 发件人地址。
2. QQ UID + 发件人地址。
3. 岗位编号或申请入口 + 发件域名。
4. 公司 + 岗位名称 + 发件人地址或域名。
5. 邮件线程、标准化主题、申请链接、发件人和时间组合。

发件人必须参与证据链，但不能单独作为同一岗位依据。完整视图快照中的严格等值匹配属于精确识别；语义搜索结果不属于。视图不完整且备用精确查询失败时不写入。

## 岗位创建与状态

- 明确的新岗位/JD：创建或合并，默认“已收藏”。
- 普通招聘宣传、宣讲会和泛职位合集只进早报，不创建岗位。
- 简历更新、补充材料、测评、AI 测评或笔试，无论信息是否完整，都先创建或复用岗位，再创建待办。
- 公司明确岗位不明：公司｜岗位待确认；岗位明确公司不明：公司待确认｜岗位；均不明：公司待确认｜岗位待确认。占位页保留邮件 ID、发件人、线程/申请链、已知信息和待确认项。
- 后续有可靠申请链证据时直接补全占位岗位，不另建；无法可靠确认时保留并列入人工确认。
- 投递成功/申请收到→已投递；测评→待测评；笔试→笔试；正式真人面试→对应轮次。
- Offer、拒信、背调仅在语义明确时更新。
- 每次更新最近邮件主题、ID、时间、发件人、发件域名、最新进度日期和可识别岗位编号。
- JD 只提取职责、要求、地点、毕业时间/申请类型、截止、编号、链接和来源。

## 简历、测评和笔试待办

- 标题：简历更新｜公司｜岗位、测评｜公司｜岗位、AI测评｜公司｜岗位、笔试｜公司｜岗位。
- 任务类型=待办，状态=待办，领域=事业；绝不创建面试页或日程。
- 截止优先使用明确时间，其次窗口结束；只有日期就写日期；某日 24:00 可记录为次日 00:00，但正文保留原文。
- 无截止则使用邮件日期，并注明“截止时间待确认”。
- 按关联岗位+类型，并结合邮件 ID、发件人、入口、截止、线程去重；提醒只更新原任务。
- 明确取消/失效→放弃；明确完成→完成。
- “下一步做什么？”不能只写“完成测评/笔试”等泛化描述。第一行写可立即执行的动作并附首选可点击入口；随后紧凑写明截止时间、平台、类型、预计时长、剩余次数，以及邮件明确给出的浏览器/设备、证件、材料、登录标识、提交方式或其他执行要求。
- 有多个链接时区分用途，例如“开始答题”“查看说明”“上传材料”；优先放最直接的执行入口。邮件只有纯文本网址时转换为可点击链接；没有链接则明确写“入口待确认”，不得虚构。
- 简历更新或补充材料任务同样在“下一步做什么？”放上传/完善入口，并写缺失材料、格式或大小要求和截止时间。
- 访问码、候选人编号等非长期凭据只有在邮件明确给出且实际执行需要时才记录；邮箱授权码、账号密码、短信/邮箱验证码等敏感凭据绝不写入 Notion。

## 真人面试

只有真人或明确安排时间的正式面试进入 [面试链路](interview-workflow.md)。测评、AI 测评和笔试不创建面试记录。

## 早报

标题：秋招邮件早报｜YYYY-MM-DD。每日早报采用“行动 + 增量”，固定只有四个一级区块：

1. 今日行动
2. 最新变化
3. 未来 7 天
4. 待补全与需确认

### 今日行动

- 以“今日建议任务”作为一份完整日计划，目标净工作量 6–8 小时，默认按约 7 小时编排；净工作量不含吃饭、通勤和休息。
- 先计算今天已有面试、笔试、测评、截止待办和其他固定承诺的预计时长，它们计入 6–8 小时；剩余时间再分配给准备、模拟、能力补缺、流程维护和复盘。
- 用有顺序的时间块呈现，不虚构具体开始时刻。每块通常为 30–120 分钟，写明优先级、预计用时、具体动作、可验收成果和关联页面链接；顶部写计划总时长。
- 日计划必须覆盖：今天到期或逾期事项；每日模拟面试及即时复盘；最近笔面试的针对性准备；能力图谱中最急的 1 个主缺口、必要时 1 个次缺口；投递/材料/待确认项维护；日终收尾和次日准备。
- 能力缺口直接嵌入对应工作块，写明能力节点和当前证据，不再另列一份重复的完整能力清单。不得根据岗位名称猜测。
- 每日模拟面试通常安排 60–90 分钟，包含准备、正式模拟和即时复盘，并链接当天模拟待办或模拟页。
- 若固定承诺已接近或超过 8 小时，只安排必要收尾，不为凑时长继续加任务；若合理工作不足 6 小时，优先补充有证据的能力练习、简历/经历素材维护或申请链补全，不制造低价值忙碌。
- 除每日模拟面试待办外，日计划中的建议默认不批量创建任务；优先链接并执行已有任务和页面。

### 计划耗时校准

- 按 [Notion 数据映射](notion-system.md) 的历史耗时校准规则读取任务与专注记录，再估算每个时间块；不得只套用固定模板时长。
- 早报在今日行动末尾增加一句“估时依据”，说明使用了哪些同类历史样本及置信度；只展示有助于判断计划的信息，不罗列原始专注记录。
- 历史记录与邮件明确时长冲突时，以邮件或正式日程为准，并将准备、复盘时间单独估算。
- 即使历史专注记录不完整，仍按用户明确要求提供 6–8 小时计划；不要把记录缺失误判为用户当天只能工作更短时间。

### 每日模拟面试任务

- 先精确查询当天已有模拟待办。若今天有真人面试对应的模拟待办，直接作为当天模拟，不再创建通用任务；不得为了日常练习改动真人面试自带模拟待办的排期。
- 今天没有针对性模拟待办时，创建或复用 `每日模拟面试｜YYYY-MM-DD`：任务类型=待办、状态=待办、领域=事业、排期只写当天日期。
- 通用模拟待办正文写今日能力重点、建议题型、预计时长、完成后要沉淀的原始问题/练习记录/能力节点；未来 7 天有真人面试时优先针对最近一场并可链接其模拟页，但不另建面试库页面。
- 按标题+任务类型+排期日期精确去重。每天最多一条通用模拟待办，不提前批量创建未来日期任务。
- 若当天已经有针对性模拟任务，则它同时满足“每日模拟面试”，严禁再建通用模拟待办；未来日期的针对性模拟不算今天已完成。
- 完成后按知识闭环更新：模拟中实际问过的问题进入原始问题库，整场训练进入能力练习库，并根据实际作答证据更新能力图谱。

### 最新变化

- 变化窗口从上一条状态为“已生成”的早报之后开始，只写新增或改变的事实，不复述静态存量。
- 包括岗位新增/合并/终态、任务截止或状态变化、面试链路变化、以及能力证据或等级变化；只显示实际发生变化的类别。
- 普通招聘宣传只有在本次新出现且对用户有信息价值时才写；登录验证、验证码等非求职信息直接忽略，不在早报中占位。
- JD 详情留在岗位页；早报只写变化摘要与链接。

### 未来 7 天

- 从明天起计算 7 天，按日期排列正式面试、模拟、复盘、简历更新、测评、笔试和其他已有任务。
- 若事项是本次新增或改期，在唯一出现的位置标注“新”或“改期”，不再复制到“最新变化”。
- 真人面试事项在一行内链接岗位、真实面试页、模拟页和三条任务，不另设重复的“面试安排”区块。

### 待补全与需确认

- 只列会影响行动或去重的缺失字段、模糊截止、占位岗位、申请链歧义和人工确认项，并写明怎样补全。
- 同一缺口不在流程风险、建议或其他区块重复描述。

### 去重表达规则

- 一个事实只放在一个区块：今天要做的放“今日行动”；明天起 7 天内发生的放“未来 7 天”；没有对应行动日期的纯变化放“最新变化”；信息缺口放“待补全与需确认”。
- 新变化若已经形成今天或未来 7 天行动，使用“新/改期”标签表达变化，不在“最新变化”再次复述。
- 删除空的二级类别，避免连续出现“无新增”；四个一级区块仍保留，内容为空时各用一句话说明。

没有新求职邮件时仍创建早报，带入 6–8 小时今日行动计划、每日模拟面试、能力补缺、未来 7 天和待补全项；“最新变化”写“自上一份已生成早报后无新增求职变化”。

## 提交 UID

全部 Notion 对象成功后，按 [脚本与数据契约](script-contracts.md) 组装 `plan.json` 并运行 `validate-plan`。只有校验 `valid=true` 后，才从脚本返回的 `pending_file` 读取 `max_uid`，在 Skill 根目录运行：

`powershell -NoProfile -ExecutionPolicy Bypass -File scripts/qq_job_mail/run_qq_mail.ps1 commit -Uid <max_uid>`

任一步失败不提交，依靠邮件 ID、发件人和数据库精确查询重试去重。
